# Спецификация: Keitaro Wrapper

## 1. Цель

Веб-приложение-обёртка над рекламным трекером [Keitaro](https://admin-api.docs.keitaro.io/),
которое упрощает работу с кампаниями типовой структуры:

* CRUD кампаний (название, гео, оффер) — со всей «обвязкой» в Keitaro, создаваемой автоматически;
* редактор потоков кампании: распределение трафика между офферами (Share), закрепление долей (Pin),
  удаление и возврат офферов, публикация изменений в Keitaro;
* статистика и тренды по офферам из отчётов Keitaro.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| KT | Keitaro |
| Кампания (Campaign) | Кампания в KT + её локальная запись в БД обёртки |
| Поток (Stream / Flow) | Правило маршрутизации внутри кампании KT |
| Оффер (Offer) | Целевая страница в KT, на которую поток распределяет трафик |
| Share | Доля трафика оффера внутри потока, целое число процентов |
| Pin | Флаг «закреплённой» доли: не пересчитывается при изменении состава офферов |
| Черновик (Draft) | Несохранённые в KT изменения потока на клиенте |

## 3. Структура кампании в Keitaro

При создании кампании обёртка создаёт в KT:

1. **Кампанию** — `type=position`, `alias` генерируется автоматически.
   Домен, группа и источник трафика берутся из конфигурации (`KEITARO_DOMAIN_ID`,
   `KEITARO_GROUP_ID`, `KEITARO_TRAFFIC_SOURCE_ID`).
2. **Flow 1 — «Geo {CC} → Google»** (`position=1`, `schema=redirect`, `action_type=http`,
   `action_payload=https://google.com`, фильтр `country accept [CC]`).
   Ловит всех посетителей из указанной страны и редиректит на Google.
3. **Flow 2 — «Offers»** (`position=2`, `schema=landings`) — распределяет остальной трафик на офферы.
   Изначально содержит выбранный оффер с долей 100%.

Если создание потоков завершилось ошибкой — кампания в KT удаляется (компенсация), пользователю
возвращается ошибка; локальная запись не создаётся.

## 4. Функциональные требования

### 4.1 Общий layout

* Общая для всего приложения шапка с Breadcrumbs.
  * Список: `Campaigns`
  * Детальная: `Campaigns / {название кампании} / Keitaro Streams`
* Элемент `Campaigns` — ссылка на список.

### 4.2 Список кампаний (`/campaigns`)

* Таблица: Name, Country, Offer, KT ID, Updated, Actions (Edit, Delete).
* Поиск по названию (регистронезависимый, debounce 300 мс, состояние в URL `?q=`).
* Пагинация на сервере (20 на страницу).
* Создание/редактирование — модальное окно с формой:
  * **Name** — обязательное, 1–255 символов;
  * **Country** — ISO 3166-1 alpha-2, выбор из списка с поиском;
  * **Offer** — выбор из офферов, доступных в KT.
* Удаление — с подтверждением; кампания удаляется в KT (переводится в архив) и локально.
  Если в KT кампании уже нет (404) — удаляется только локальная запись.
* Клик по строке — переход на детальную страницу.

Поведение при редактировании:

| Поле | Действие в KT |
|---|---|
| Name | `PUT /campaigns/{id}` |
| Country | `PUT /streams/{flow1}`: новое имя потока и фильтр страны |
| Offer | в Flow 2 новый оффер заменяет предыдущий основной: он добавляется (или возвращается) с долей старого, старый становится удалённым (серым) |

### 4.3 Детальная страница (`/campaigns/:id`)

Шапка страницы: название кампании, гео, оффер и кнопки:

* **Fetch streams from KT** — загружает потоки из KT и сливает с локальными данными (см. §5.2);
* **View in KT** — открывает `{KEITARO_URL}/#!/campaigns/{kt_id}` в новой вкладке.

Ниже — таблица со столбцами **Name, Share, Stats, Trends, Actions**. В таблице два потока:
первым идёт основной поток с офферами (Flow 2), вторым — поток-редирект без офферов (Flow 1).
Номер потока в заголовке — его позиция в KT.

Для каждого потока:

* **Заголовок потока** — строка на всю ширину: `Stream: Flow {N}: {name}`.
  При наличии несохранённых изменений справа появляются **Push to KT** и **Cancel**,
  а при невалидном распределении долей — текст ошибки (Push недоступен).
* **Строки офферов** (только у потока с офферами):
  * Name — `#{id} {название}`;
  * Share — поле с процентом и кнопка **Pin** (закрепить/открепить);
  * Stats — клики / конверсии / доход за 7 дней;
  * Trends — спарклайн кликов по дням за 7 дней;
  * Actions — **Remove** или **Bring back**.
* **Строка добавления** — на всю ширину: Select по всем офферам KT, которых ещё нет в потоке,
  и кнопка **Add**.
* У потока-редиректа вместо офферов — строка с описанием правила (`Country = DE → https://google.com`)
  и его статистикой.

Визуальные состояния строки оффера:

| Состояние | Вид | Share | Action |
|---|---|---|---|
| Активный, без изменений | обычный | текущая доля | Remove |
| Удалён в черновике | серый текст, жёлтый фон | 0% | Bring back |
| Добавлен / возвращён в черновике | жёлтый фон | рассчитанная доля | Remove |
| Доля изменилась в черновике | жёлтый фон ячейки Share | новая доля | Remove |
| Удалён и опубликован (или удалён в KT) | серый текст | 0% | Bring back |

### 4.4 Правила распределения долей

Применяются к активным офферам потока при любом изменении состава (Add / Remove / Bring back /
Pin / ручной ввод):

1. Удалённые офферы: `share = 0`, `pinned = false`.
2. `pinnedSum` = сумма долей закреплённых активных офферов.
3. `rest = 100 − pinnedSum` делится поровну между незакреплёнными активными офферами;
   остаток от деления раздаётся по 1% первым по порядку офферам
   (например, 3 оффера → 34 / 33 / 33).
4. Ручной ввод доли автоматически закрепляет оффер (Pin).
5. Валидность черновика (иначе Push недоступен, показывается причина):
   * `pinnedSum ≤ 100`;
   * если активные офферы есть — сумма долей равна 100;
   * если незакреплённых активных офферов нет, то `pinnedSum` должен быть ровно 100.
6. Поток без активных офферов публиковать можно (трафик потока не будет распределяться) —
   показывается предупреждение.

Доли, полученные из KT, отображаются как есть до первого изменения черновика.

### 4.5 Публикация и синхронизация

* **Push to KT** — `PUT /streams/{id}` с полным списком активных офферов и их долями.
  Офферы, отсутствующие в списке, удаляются из потока в KT. Ответ KT сохраняется локально.
  Удалённые офферы остаются в локальной БД (серые, 0%, Bring back).
* **Cancel** — сбрасывает черновик к последнему сохранённому состоянию.
* **Fetch streams from KT** — см. §5.2. Если есть несохранённый черновик, перед загрузкой
  запрашивается подтверждение (черновик будет сброшен).

## 5. Данные

### 5.1 Модель БД (PostgreSQL)

```
campaigns
  id               serial PK
  name             varchar(255) not null           -- индекс для поиска
  country_code     char(2) not null
  offer_id         int not null                    -- основной оффер (ID в KT)
  kt_campaign_id   int unique not null
  kt_alias         varchar(64) not null
  created_at, updated_at  timestamptz

streams
  id               serial PK
  campaign_id      FK → campaigns ON DELETE CASCADE
  kt_stream_id     int unique not null
  name             varchar(255)
  position         int
  schema           varchar(32)    -- redirect | landings | ...
  action_payload   text null      -- URL редиректа
  country_filter   varchar[]/json -- страны из фильтра (для отображения)
  synced_at        timestamptz

stream_offers
  id               serial PK
  stream_id        FK → streams ON DELETE CASCADE
  offer_id         int not null       -- ID оффера в KT
  offer_name       varchar(255) null  -- снапшот названия
  share            int not null (0..100)
  pinned           bool not null default false
  is_active        bool not null      -- false = удалён (серый)
  sort_order       int not null       -- порядок отображения (порядок добавления)
  UNIQUE (stream_id, offer_id)
```

### 5.2 Слияние потоков при Fetch

Для каждого потока кампании из KT (upsert по `kt_stream_id`):

* оффер есть в KT → `is_active = true`, `share` из KT, `pinned` сохраняется из БД;
* оффер есть в БД, но отсутствует в KT → `is_active = false`, `share = 0`, `pinned = false`
  (**оффер не пропадает**, становится серым с Bring back);
* новый оффер из KT → добавляется в конец списка;
* потоки, удалённые в KT, удаляются локально.

## 6. REST API обёртки

Префикс `/api`. Ошибки: `{"detail": "..."}`; ошибки KT → `502` с текстом ошибки KT;
недоступность KT → `503`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/health` | healthcheck |
| GET | `/meta` | `{ keitaro_url }` |
| GET | `/offers` | офферы KT (кэш 60 с) |
| GET | `/campaigns?q=&limit=&offset=` | список `{items, total}` |
| POST | `/campaigns` | создание (KT + БД) |
| GET | `/campaigns/{id}` | кампания |
| PATCH | `/campaigns/{id}` | редактирование |
| DELETE | `/campaigns/{id}` | удаление |
| GET | `/campaigns/{id}/streams` | потоки и офферы из БД |
| POST | `/campaigns/{id}/streams/sync` | Fetch from KT + слияние |
| PUT | `/campaigns/{id}/streams/{stream_id}/offers` | Push черновика в KT |
| GET | `/campaigns/{id}/stats?days=7` | статистика по потокам/офферам + по дням |

Тело Push:

```json
{ "offers": [ { "offer_id": 18813, "share": 60, "pinned": true, "is_active": true } ] }
```

Сервер валидирует: уникальность офферов, `0 ≤ share ≤ 100`, сумма активных = 100
(если они есть), у удалённых `share = 0`.

Статистика: `POST /report/build` KT, измерения `stream_id, offer_id, day`,
метрики `clicks, conversions, revenue`, фильтр `campaign_id`, интервал — последние N дней.

## 7. Нефункциональные требования

* **UX**: skeleton-лоадеры при первой загрузке, спиннеры на кнопках при мутациях,
  блокировка повторных нажатий, сохранение предыдущих данных при поиске/пагинации
  (без «дёрганий»), фиксированная высота строк и ширина колонок, toast-уведомления об успехе/ошибке,
  экраны ошибок с кнопкой Retry, 404 для несуществующей кампании.
* **Надёжность**: таймауты запросов к KT (15 с), понятные сообщения об ошибках KT,
  компенсация при частичном создании кампании.
* **Безопасность**: API-ключ KT хранится только на бэкенде (`.env`), во фронтенд не попадает.
* **Качество**: ruff + mypy (backend), ESLint + Prettier + tsc (frontend), commitlint,
  CI в GitHub Actions; тесты критичных участков:
  * алгоритм распределения долей и редьюсер черновика (Vitest);
  * слияние потоков, валидация Push, создание кампании с компенсацией, CRUD API (pytest, KT замокан).

## 8. Стек

* Backend: Python 3.11+, FastAPI, SQLAlchemy 2 (async) + asyncpg, Alembic, httpx, Pydantic v2.
* Frontend: TypeScript, React, Vite, Tailwind CSS, shadcn/ui, TanStack Query, React Router,
  react-hook-form + zod.
* Инфраструктура: Docker Compose (Postgres, backend, frontend на nginx).

## 9. Вне рамок

* Аутентификация пользователей обёртки.
* Редактирование других параметров кампаний/потоков KT (домен, группа, источник задаются конфигом).
* Одновременное редактирование одного потока несколькими пользователями (последний Push побеждает).
